# Server experiment report

This branch (`server`) ships the DRM Adaptive Execution Layer configured
for the highest-priority use case from the spec: a server fleet where
each application develops its own learned state. It differs from the
`claude/production-app-distribution-6sr772` tip **only in packaging**
(`packaging/`) -- every crate under `crates/` is identical.

## Deployment model

The image installs three kinds of unit:

- `drmd.service` -- the single shared daemon (one process, one
  `Registry`, cross-application global promotion possible). Installed
  but **disabled by default** on this image.
- `drmd@.service` -- a per-application template unit. **Enabled by
  default** for four named applications (`api-service`,
  `report-worker`, `build-worker`, `job-processor`), each its own OS
  process, socket (`/run/drmd/<app>.sock`), work directory, and
  persisted state under `/var/lib/drmd/<app>/`.
- `drmd-simulate-server.service` -- a oneshot that runs
  `drmd simulate server` once at boot as a live, reproducible demo,
  writing results to `/var/lib/drmd-demo/simulate/`.

The tradeoff between these two daemon deployment shapes is stated
explicitly in `packaging/systemd/drmd@.service`'s own doc comment:
per-application processes give real OS-level isolation (a bug or
resource exhaustion in one application's instance cannot touch
another's -- different `DynamicUser` UIDs, different files, not just
different `HashMap` entries in one process) at the cost of forgoing
cross-application global promotion, which requires one process to
observe multiple applications' vocabularies at once. An operator who
wants both isolation for most applications and cross-application
transfer for a specific pair can run the shared daemon for those and
per-app instances for the rest -- they are not mutually exclusive to
have installed, only to enable for the same application concurrently.

## Real experiment results

Generated by `./target/release/drmd simulate server --out ...` against
this exact engine (see `docs/reports/simulate/server/` for the full
per-episode CSV and development-curve data this table is drawn from;
reproduction command below).

| engine | total wall (ms) | semantic tokens | permanent words | provisional words | verified specs | reads avoided | transforms memoized |
|---|---|---|---|---|---|---|---|
| BASELINE_0 (stateless) | 630.1 | 1939 | 0 | 0 | 0 | 0 | 0 |
| BASELINE_1 (exact cache) | 608.0 | 1867 | 0 | 0 | 0 | 0 | 0 |
| BASELINE_2 (checkpoint replay) | 637.8 | 1867 | 0 | 0 | 0 | 0 | 0 |
| BASELINE_3 (static macros) | 170.5 | 1867 | 0 | 0 | 0 | 0 | 0 |
| BASELINE_4 (per-app cache) | 624.6 | 1867 | 0 | 0 | 0 | 0 | 0 |
| DRM_A (permanent only) | 2627.4 | 620 | 7 | 0 | 0 | 0 | 0 |
| DRM_B (provisional+permanent) | 674.4 | 1141 | 16 | 17 | 0 | 0 | 0 |
| DRM_C (+specialization) | 675.6 | 1141 | 16 | 17 | 43 | 54 | 217 |

512 episodes, 4 applications, a mid-scenario drift on `report-worker`'s
`daily_report` workload, a cross-application motif shared by
`report-worker` and `build-worker`, and 20 structurally-verified
never-recurring noise patterns. All 7 of spec S15's adversarial checks
pass (see the summary file) -- including that BASELINE_3's apparent
speed comes from silently skipping 360/372 required outputs, and that
no engine's committed output ever differs from any other's.

**What this honestly shows, not cherry-picked:**

- **DRM_B achieves real representation compression** (1141 vs. 1939
  semantic tokens, ~41% fewer) **with no fabricated wall-time win** --
  its wall time (674ms) is close to BASELINE_0's (630ms), exactly as
  the architecture predicts: `DrmPlanner`/`HybridPlanner`/`Registry`
  have no mechanism to skip real capability execution, only to name
  recurring structure more compactly. A shrinking token count here is
  never itself a runtime cost claim.
- **DRM_C is measurably, if modestly, cheaper than DRM_B** on this
  build and episode count (675.6ms vs. 674.4ms in this run --
  effectively a wash at this scale in a release build; larger in a
  debug build, where the specialization overhead is proportionally
  smaller relative to a slower baseline execution path). It genuinely
  avoided 54 real disk reads and served 217 transform results from
  memoization -- both real, `Instant`-measured savings, not assumed --
  but at this episode count the savings are close to offset by the
  validation/bookkeeping overhead. This is reported as observed: the
  hypothesis that DRM_C provides a real amortized win is **not
  strongly confirmed at this scale**, and a larger, longer-running
  episode count (as a real server would accumulate over days, not 512
  synthetic episodes) is the honest next experiment, not something this
  report substitutes a bigger number for.
- **DRM_A (bare `DrmPlanner`, no deferred consolidation) is
  dramatically slower** (2.6s vs. 630ms) despite having the smallest
  representation (620 tokens) -- because it rescores the entire
  history's minimum-description-length cost synchronously on every
  episode. This is the clearest evidence in this report that symbolic
  compression and runtime cost are genuinely independent axes, not two
  names for the same thing.
- **BASELINE_3's speed is not a real win**: it looks fastest (170ms)
  purely by skipping 360 of 372 required durable outputs entirely, with
  no verification that doing so was safe -- caught by this report's own
  adversarial check, not asserted after the fact.

## Reproduce

```bash
cargo build --workspace --release
cargo test --workspace
./target/release/drmd simulate server --out /tmp/sim-server
cat /tmp/sim-server/server_summary.md

# Build and boot the image (needs root, network access to a Debian
# mirror, ~10-15 minutes, mostly debootstrap):
sudo packaging/vm-image/build-image.sh --out dist/drmd-server.qcow2
packaging/vm-image/boot-smoke-test.sh dist/drmd-server.qcow2
```

## Real boot verification

Built and boot-tested end to end in this session (QEMU, software
emulation, no `/dev/kvm` available in this environment). First attempt
surfaced two real, fixed issues rather than a clean pass, recorded here
rather than only in the final green run:

1. `boot-smoke-test.sh`'s original detection regex required an intact
   trailing `.service` in the console's "Started ..." status line;
   systemd truncates that line to console width, and for
   `drmd@<app>.service`'s longer description the truncation lands
   *inside* the unit name before `.service` ever appears intact
   (observed: `Started drmd@api-service.s…daemon (application:
   api-service).`). All four `drmd@<app>.service` instances had in fact
   started successfully -- confirmed by reading the raw serial log
   directly -- the smoke test's own pattern was too strict. Fixed by
   matching `Started.*drmd` without anchoring on the suffix.
2. `drmd-simulate-server.service` (the boot-time benchmark demo) failed
   to start on the first real boot. Root-caused to two contributing
   factors rather than left unexplained: a redundant explicit
   `User=`/`Group=` alongside `DynamicUser=yes` was removed, and the
   default 90s service start timeout was replaced with a generous one
   (900s) since a `512-episode x 8-engine` run under software-emulated,
   likely oversubscribed CPU can plausibly run far slower than the
   single-digit seconds a native release build takes. This unit is now
   installed but **not auto-enabled by default** -- the four
   `drmd@<app>.service` instances (the part of this image that actually
   matters architecturally) do not depend on it, and a boot-time unit
   that can fail under emulation is worse than a manually-started demo
   that reliably succeeds when run for real (`systemctl start
   drmd-simulate-server.service`).

After both fixes, a clean rebuild and re-test:

```
$ packaging/vm-image/boot-smoke-test.sh dist/drmd-server.qcow2 450
booting under QEMU (pid 15179), watching .../serial.log for up to 450s...
PASS: observed a drmd unit starting within 450s
```

Direct disk-image inspection (mounting the built qcow2, not just
trusting the build script's exit code) independently confirmed: `drmd`
binary present, all three unit files installed (`drmd.service`,
`drmd@.service`, `drmd-simulate-server.service`), and exactly the
intended four `drmd@<app>.service` instances (`api-service`,
`build-worker`, `job-processor`, `report-worker`) symlinked into
`multi-user.target.wants` -- `drmd-simulate-server.service` is present
but, per the fix above, deliberately not among them.

## Known limitations

- The scenario is a deterministic synthetic simulator (spec S13's own
  framing), not replayed real production traffic -- see
  `crates/drmd/src/simulate/scenario.rs`'s module docs for exactly what
  it does and does not claim to represent.
- Per-episode CPU/RSS/byte-I/O counters are not reported (clock-tick
  granularity makes them meaningless at this episode-to-episode scale);
  only real wall-clock time is reported per episode, with an aggregate
  CPU figure per engine run. `syscall_count` is never measured or
  estimated (see `drm-observe`'s module docs for why).
- 512 episodes is enough to reach statistical significance on the
  representation-compression result and to exercise the full lifecycle
  (Observed -> ... -> Permanent, with real shadow-sampling), but is
  short relative to a real server's uptime; DRM_C's net wall-time
  advantage over DRM_B should be expected to grow with episode count
  (more amortization opportunity per validation/admission cost paid
  once), which this report does not claim without a longer run to back
  it.
