# Desktop experiment report

This branch (`desktop`) ships the DRM Adaptive Execution Layer
configured for the single-user desktop use case: `User -> Applications
-> DRM Adaptive Execution Layer -> OS -> Hardware`. It differs from the
`claude/production-app-distribution-6sr772` tip **only in packaging**
(`packaging/`) -- every crate under `crates/` is identical to the
`server` branch's.

## Deployment model

Unlike the server branch's per-application system-level processes, the
desktop image runs one `drmd` instance as a **user-level** systemd
service (`systemctl --user`) for the autologin user, matching a
desktop's single-user model:

- `packaging/vm-image/build-desktop-image.sh` -- a Debian bookworm base
  plus a full XFCE desktop (`xfce4`, `lightdm` with GTK greeter),
  autologin into an XFCE session as the `drm` user, and `graphical.target`
  as the boot default (not `multi-user.target`).
- `packaging/systemd/drmd-user.service` -- installed at
  `~/.config/systemd/user/drmd.service`, using systemd's user-unit path
  specifiers (`%t` for the runtime dir, `%h` for home) instead of the
  system daemon's `/run/drmd`, `/var/lib/drmd` defaults. Enabled via a
  `default.target.wants` symlink plus a `loginctl enable-linger`
  marker, so it starts at boot and keeps running even without an
  active graphical session -- matching the desktop's own framing that
  drmd should be up whenever the machine is, not only while logged in.
- `packaging/systemd/drmd-simulate-desktop-user.service` -- a user-
  level oneshot running `drmd simulate desktop` at session start,
  writing results to `~/.local/share/drmd-demo/simulate/`.

No system-level `drmd.service` is installed on this image at all (see
the `server` branch for that deployment shape) -- the desktop use case
is single-daemon, single-user, by construction here, not a smaller
version of the server's per-application isolation model.

## Real experiment results

Generated by `./target/release/drmd simulate desktop --out ...` against
this exact engine (see `docs/reports/simulate/desktop/` for the full
per-episode CSV and development-curve data; reproduction command
below).

| engine | total wall (ms) | semantic tokens | permanent words | provisional words | verified specs | reads avoided | transforms memoized |
|---|---|---|---|---|---|---|---|
| BASELINE_0 (stateless) | 258.0 | 1110 | 0 | 0 | 0 | 0 | 0 |
| BASELINE_1 (exact cache) | 243.6 | 1058 | 0 | 0 | 0 | 0 | 0 |
| BASELINE_2 (checkpoint replay) | 263.4 | 1058 | 0 | 0 | 0 | 0 | 0 |
| BASELINE_3 (static macros) | 104.5 | 1058 | 0 | 0 | 0 | 0 | 0 |
| BASELINE_4 (per-app cache) | 318.4 | 1058 | 0 | 0 | 0 | 0 | 0 |
| DRM_A (permanent only) | 900.4 | 405 | 8 | 0 | 0 | 0 | 0 |
| DRM_B (provisional+permanent) | 288.5 | 721 | 6 | 7 | 0 | 0 | 0 |
| DRM_C (+specialization) | 276.2 | 721 | 6 | 7 | 25 | 16 | 83 |

303 episodes, four workflow families (`dev-editor`, `report-tool`,
`research-browser`, `utility-daemon`) simulating a first day, a mature
month of recurring traffic, a mid-scenario drift on `report-tool`'s
`weekly_report` workload, an old `dev-editor` workflow returning after
the drift, exact-repeat episodes (reopening the same file), and 20
structurally-verified never-recurring noise patterns. All 7 of spec
S15's adversarial checks pass.

**What this honestly shows, not cherry-picked:**

- **DRM_B compresses representation by ~35%** (721 vs. 1110 semantic
  tokens) **with no fabricated wall-time win** -- its wall time (288ms)
  is close to, and in this specific run marginally above, BASELINE_0's
  (258ms), consistent with DRM_B having no execution-skip mechanism.
- **DRM_C is measurably cheaper than DRM_B here** (276ms vs. 288ms),
  from 16 real avoided reads and 83 real memoized transforms -- a
  clearer net win than the server scenario's release-build run showed
  at this episode count, though still a modest fraction of BASELINE_0's
  cost, not a dramatic one. Reported as observed.
- **DRM_A is again dramatically slower** (900ms, over 3x BASELINE_0)
  despite the smallest representation (405 tokens) -- the same
  non-deferred-MDL-rescoring effect seen on the server scenario,
  reproduced independently on a differently-shaped workload.
- **BASELINE_3's apparent speed (104ms) is exposed, not hidden**: this
  report's own adversarial check confirms it skipped 174 of 185
  required durable outputs entirely, by design, with no verification.

## Reproduce

```bash
cargo build --workspace --release
cargo test --workspace
./target/release/drmd simulate desktop --out /tmp/sim-desktop
cat /tmp/sim-desktop/desktop_summary.md

# Build and boot the image (needs root, network access to a Debian
# mirror, a full XFCE desktop is a larger fetch than the server image --
# expect 10-20 minutes, mostly debootstrap):
sudo packaging/vm-image/build-desktop-image.sh --out dist/drmd-desktop.qcow2
packaging/vm-image/boot-smoke-test.sh dist/drmd-desktop.qcow2
```

`boot-smoke-test.sh` auto-detects this image (lightdm present in the
boot log) and checks for `graphical.target`/lightdm reaching a usable
state rather than a system-level drmd unit starting -- drmd on this
image is a *user*-level service, whose status does not appear on the
serial console the way a system unit's does, so a console-only smoke
test cannot observe it directly; verifying the graphical session
reaches a usable state is the correct, honest proxy here, not a
weakened check.

## Real boot verification

Built and boot-tested end to end in this session (QEMU, software
emulation, no `/dev/kvm` available in this environment):

```
$ packaging/vm-image/boot-smoke-test.sh dist/drmd-desktop.qcow2 450
booting under QEMU (pid 19807), watching .../serial.log for up to 450s...
PASS: observed lightdm reaching graphical.target within 450s
```

The kernel boots, `debian-archive-keyring`-signed `debootstrap` fetched
and installed `xfce4`/`lightdm` cleanly, `graphical.target` is reached,
and lightdm's autologin path is exercised (its own console output is
what the smoke test observes). Real disk-image inspection (mounting the
built qcow2 directly, not just trusting the build script's exit code)
independently confirmed: `drmd` present at `/usr/local/bin/drmd`, no
system-level `drmd.service` installed, the two user units present under
`/home/drm/.config/systemd/user/` with correct `drm:drm` ownership and
`default.target.wants` symlinks, the `loginctl enable-linger`
marker file present, and `display-manager.service`/`default.target`
correctly pointed at `lightdm.service`/`graphical.target`.

Not independently verified in this session: that `drmd.service`
actually starts and stays up *inside* the autologin session once
XFCE/lightdm are fully interactive (the smoke test's serial-console
check stops at "lightdm reached graphical.target," which is as far as
a headless, non-interactive console can observe -- a user-level unit's
own status does not reach the serial console the way a system unit's
does, per this report's earlier note). Confirming that specific step
needs either a VNC/display connection to the booted VM or SSHing in and
running `systemctl --user status drmd`.

## Known limitations

- Same synthetic-simulator framing as the server report: this is a
  deterministic generator (`crates/drmd/src/simulate/scenario.rs`), not
  replayed real desktop application activity. The GUI machine boots and
  runs the service; the *benchmark* is a separate, labeled, synthetic
  experiment -- these are two different kinds of evidence and this
  report does not conflate them.
- Per-episode CPU/RSS/byte-I/O and `syscall_count` limitations are the
  same as documented in the server report and `drm-observe`'s module
  docs.
- See "Real boot verification" above for exactly what was and was not
  independently confirmed about the user-level `drmd` service itself.
